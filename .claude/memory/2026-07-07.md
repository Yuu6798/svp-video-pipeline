### Design Decisions

- **ルール表現**: `ScenarioContext`（frozen dataclass、locks/risk_flags/
  detailed_background/character_weapon_contact/background_forbidden/
  reflection_forbidden/role_visual_cue_role 等の事前計算済みフラグ）+
  `LayerRule`（`layer` ドット表記パス、`list_appends`/`sets`
  各ドット部分パス→静的 tuple または `Callable[[ScenarioContext], ...]`、
  `when` ガード）。`apply_scenario` は `layer` + サブパスを連結した単一の
  ルート相対パスに対して汎用の再帰 `_get_path`/`_set_path`
  （pydantic `model_copy` チェーン）で読み書きする 1 実装に統一した。
- **when の意味論**: シナリオ全体の早期 return ゲート（旧
  `if not locks: return svp` 等）は `planner.py` の `_apply_*` に残し
  （検出ヘルパー 1054–1509 行は無改修）、シナリオ内の一部レイヤーのみ
  スキップする条件（background_noise の pose_layer 武器接触ゲート）だけを
  `LayerRule.when` に対応させた。両者は最終 `svp` の到達不能な同値性が
  保証される（`model_copy(update=...)` は指定キーのみ上書きするため）。
- **role_visual_cue.role のフォールバック**: `svp.role_visual_cue.role or
  "character"` は元の `svp`（変更前）の値に依存するため、`ctx` 構築時に
  `role_visual_cue_role=svp.role_visual_cue.role` として事前確定し、
  ルール側は `ctx` のみ参照する純粋な `Callable[[ScenarioContext], Any]`
  に統一した（同一シナリオ内で role_visual_cue を先行して書き換える
  ルールが無いため安全）。
- **katana_reflection の pose_layer.forbidden の非対称性発見**: 元コードの
  `_build_katana_reflection_pose_layer` は `reflection_forbidden`（6 項目、
  "katana reflection on glass, umbrella, rain..." を含む）を使わず、
  別建ての 5 項目リテラルリストを使用していた。移記時に逐一 diff
  照合し、この非対称性を保持した（見落とすと composition/style/c3 とは
  異なる pose_layer.forbidden の項目数がテストで検出されずに変わる
  リスクがあった）。
- **200 行削減の達成**: 初回実装は 1509→1310 行（199 行減、AC 未達）
  だったため、`planner_rules.py` のモジュール docstring 1 段落を圧縮して

- **ENV-1 削除前の再確認**: 削除前に `grep -rn DEFAULT_IMAGE_MODEL` を
  リポジトリ全体で再実行し、ヒットが `.env.example` 自身と STATUS.md の
  Queue 行（今回削除対象）のみであることを確認してから削除した。専用の
  隣接コメント行は無かったため該当 1 行のみ削除した。
- **LOG-1 は `_build_log_data` 内の再帰丸めで実装**: 各 stage 構築箇所
  （`_load_or_plan_svp`/`_run_image_stage`/`_run_video_stage` 等、数十
  箇所に散在）を個別に書き換えるのは Design Memo のスコープ
  （「log データ構築箇所での丸めに限定」）を超え変更面積も大きくなる
  ため、`_build_log_data` の戻り値構築時に `_round_log_floats`（dict/list
  を再帰走査し float のみ `round(x, 4)`）を `stages` に、`_round_log_float`
  を `total_cost_usd`/`total_elapsed_sec` に適用する一箇所集約の設計に
  した。`cost_usd`/`elapsed_sec`/`estimated_cost_usd` に限らず将来 stage
  dict に float フィールドが増えても自動的に丸められる（Design Memo の
  「他に float があれば同様」を満たす）。None はそのまま通す
  （`_round_log_float` は None ガード、`_round_log_floats` は
  `isinstance(data, float)` のみに反応するため non-float は無変更）。
- **既存テストの期待値は無変更で済んだ**: `test_pipeline.py` の
  float アサーションは `== 0.0`（丸めても不変）/`> 0`/`== 0.032`
  （既に 4 桁以内）のみで、full-precision に依存するものが無かった。
  よって Design Memo が想定した「期待値更新」は本セッションでは発生
  しなかった（更新不要と確認した旨のみ記録）。
- **新規テストは実測 elapsed_sec で丸めを検証**: 合成 float ではなく
  `pipeline.run()` を実行し、`time.perf_counter()` 由来の実測 elapsed_sec
  （通常 4 桁を超える精度を持つ）を含む log.json 全体を再帰走査して
  `value == round(value, 4)` を assert する構成にした。合成値だけでは
  丸めの有無に関わらず偶然 pass しうるため、実測パスで検証する方が
  回帰検出力が高いと判断した。
- **coverage の CI ゲート化は見送り**: 閾値基準値の選定が必要でローカル
  計測は pytest-cov で確保済み。coverage 計測が定常運用に乗った時点で
  再検討。
